# ADR-0004 · 恢复不完整历史要报错不猜

| 项 | 内容 |
|---|---|
| **状态** | 已采纳（Accepted） |
| **日期** | 2026-11-21（初版） |
| **背景** | 进程死在任意两个提交点之间，恢复时读出来的会话历史有三种可能：**完整**、**没有这一段**、**半截**（assistant 已经请求了工具，但工具结果缺失）。前两种正常，第三种只可能来自外部篡改或实现漂移——它不是运行时会自然产生的状态。 |
| **决策** | 回填与提交放在同一段顺序代码里，保证「要么完整要么没有这一段」；遇到**半截历史**一律 fail-closed 报错，**不猜、不补、不跳过**。结果无法确认（远端是否生效不可知）时显式上抛 `res.Uncertain`，禁止盲目重试。 |
| **后果** | ① 恢复后的历史可直接信任，不会带着一段被编造出来的工具结果继续跑；② `Uncertain` 把「不知道」变成一等公民——宿主必须显式处理它，而不是当成失败重试；③ 代价：少数「历史真被外部改过」的场景会从「静默继续」变成「显式报错」，这是刻意选的失败形态。 |
| **依据** | 仓内 README「恢复语义（本层的要点）」一节；`agentloop` 与 `runtime` 的端到端用例（含「施加次数仍为 1」的断言）。 |

> **一句话结论**：历史不完整是异常不是状态——恢复出来的历史要么完整要么没有这一段，中间态 fail-closed 报错，不猜。

---

## 三种恢复结果

| 恢复出来的历史 | 判定 | 处置 |
|---|---|---|
| 完整 | 正常 | 按续跑计划继续 |
| 缺一段（提交点之间死亡） | 正常 | 按续跑计划继续（这段本来就没发生过） |
| 半截（assistant 请求了工具但结果缺失） | **异常** | fail-closed 报错，不猜 |

第三种之所以是异常：运行时自己产生历史时，工具结果与 assistant 回合是**一起提交**的，
半截状态在进程内部不可能出现。它出现了，说明有人在运行时之外动过数据，
或者实现本身漂了。这两种情况下**任何猜测都是编造**。

## 幂等闸与恢复是同一件事的两面

恢复时模型可能重放同一个工具调用。此时闸判 `replayed`，**执行体不会被再次调用**——
这条由 `agentloop` 与 `runtime` 的端到端用例钉住（施加次数恒为 1）。

闸之所以能判 `replayed`，靠的是幂等键：默认是编排侧铸造的 `toolCallID`。
同一进程内的重放它一定稳定；**跨副本接管就不一定**——那正是 ADR-0005 的前提。

## `Uncertain` 为什么不能当失败

`res.Uncertain` 的含义是「不知道远端到底生效没有」。把它当成失败去重试，
等于用一个不确定的动作去覆盖另一个不确定的动作；把它当成成功，等于宣布一件没验证的事。
它必须由宿主显式处理——通常是把「可能已经生效」这件事交给业务对账，
而不是由运行时替宿主决定。
