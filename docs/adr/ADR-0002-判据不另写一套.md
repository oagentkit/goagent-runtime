# ADR-0002 · 判据不另写一套

| 项 | 内容 |
|---|---|
| **状态** | 已采纳（Accepted） |
| **日期** | 2026-11-21（初版） |
| **背景** | runtime 是「装配层」，最容易被写成「顺手把判据也实现一遍」的第二个内核。装配层确实要碰存储、事件、幂等——看上去不实现一遍就「不完整」。但一旦本仓自己写了一套幂等判定，集群里就会出现两套「什么算同一个副作用」的口径，两套口径必然在某处漂移，而漂移的形态是**看起来都合理**。 |
| **决策** | 状态机 / 幂等闸 / 预算守卫 / 恢复 / 抢占与接管代次，**全部来自 goagent-kernel 的契约面**；本仓只做接线，不另写第二套判据。新存储实现必须跑 kernel 的 `sidetest` 共享契约套件；本仓对 kernel 的 import 只允许契约面（checkpoint / controlplane / eventbus / sideeffect / sidetest / taskboard / tenant）。 |
| **后果** | ① 内存、SQLite、PG 三个副作用闸实现跑**同一套**共享契约套件，口径不可能分叉；② kernel 改判据时，本仓的三个实现同时被契约套件覆盖，不需要逐个跟改；③ 代价是本仓必须跟 kernel 的契约面走，kernel 的契约变更对本仓是破坏性变更（要走发版与升级说明）。 |
| **依据** | 仓内 AGENTS.md「边界纪律 · 不复制内核判据」；kernel 的 `sidetest` / `taskboard` / `sideeffect` / `roundguard` / `eventbus` 契约包。 |

> **一句话结论**：判据归 kernel，本仓只接线——装配层最容易腐化成「顺手把判据也实现一遍」的第二个内核。

---

## 「顺手实现一遍」是典型的腐化路径

过程通常是这样的：宿主要一个新能力，本仓缺一个判据，于是先在本地实现一版，
跑通了，再回头想「要不要提回 kernel」。多数时候这个「回头」不会发生——
因为本地那版已经能用了。于是仓里出现两个口径：kernel 的和本仓的。

漂移不会立刻出事。它会在某次两边对同一现象给出不同结论时才出事，而那时
没人知道该信谁。

## 怎么守住：契约套件

守法不是靠自觉，是靠**判据**：

- 任何新的存储实现，必须跑 kernel 的 `sidetest` 共享契约套件；
- 本仓对 kernel 的 import 只允许契约面（清单见 AGENTS.md）；
- 契约套件本身归 kernel——本仓改不动它，也不需要改它。

判据本体与判据的适用范围分开，是这一条能落地的关键：
本仓可以说「我实现了 PG 的副作用闸」，但不能说「我定义了副作用闸」。

## 判据归属速查

| 语义 | 归属 |
|---|---|
| 状态机 / 续跑契约 | kernel |
| 副作用幂等闸（什么算同一次） | kernel |
| 回合预算 / 守卫 | kernel |
| 恢复语义（快照 → 续跑计划） | kernel |
| 抢占 / 租约 / 接管代次 | kernel |
| 跨副本事件面 | kernel |
| 模板选型 / 默认口径 / 接线 | **本仓** |
| 模型供应商适配 / 系统提示 / 工具实现 | 宿主 |
