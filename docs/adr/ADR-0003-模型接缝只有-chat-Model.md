# ADR-0003 · 模型接缝只有 chat.Model

| 项 | 内容 |
|---|---|
| **状态** | 已采纳（Accepted） |
| **日期** | 2026-11-21（初版） |
| **背景** | Agent 运行时要调模型。最小实现是直接 import 某家 SDK：拿 client、传 messages、读 response。这样写出来的库只能给用这家供应商的人用，而「换一家模型」对宿主是产品需求，不是重构需求。 |
| **决策** | 模型接缝只有 `chat.Model` 一个窄接口——只有一个 `Chat` 方法，消息类型自带。**本仓不 import 任何具体供应商 SDK**；任何模型 SDK 由宿主包一层适配接入。 |
| **后果** | ① 换供应商是宿主侧新增一个适配文件，不是改本仓；② 本仓依赖面窄（模型侧零依赖），可测性不依赖网络；③ 代价是适配层要宿主自己写——这是**有意的代价**：把供应商差异留在宿主，本仓保持供应商中立。 |
| **依据** | 仓内 README「最小接入」一节；AGENTS.md「chat.Model 是唯一的模型接缝」。 |

> **一句话结论**：模型接缝只有 `chat.Model` 一个窄接口——供应商中立是接缝纪律，不是偏好。

---

## 接缝窄到只剩一个方法

```go
type Model interface {
    Chat(ctx context.Context, req Request) (Response, error)
}
```

窄接口的价值在**换供应商时不需要动运行时**：适配器在宿主侧实现这个接口，
运行时不知道也不关心底下是哪一家。接缝一旦带上供应商概念（比如带 `Usage` 的
某家特有结构体、或接受某家的 `ToolChoice`），窄接口就退化成了「换壳的耦合」。

## 为什么不是「在本仓加个适配器包」

在本仓加 `chat/openai` 这类包看起来更方便，但它把供应商**版本升级**变成
本仓的发版事件：供应商改一次接口，本仓就要发一次版，宿主才能升级。
把适配留在宿主侧，供应商升级就只是宿主仓的一次改动。

## 代价（明写出来）

宿主第一次接入要多写一个文件。这是刻意的：**接缝的价值在第一次看起来最费劲**——
如果供应商中立没有成本，那它多半不是接缝，只是口号。
