# runtime 是什么

**goagent-runtime 是 [goagent-kernel](https://github.com/oagentkit/goagent-kernel) 的装配层。**

kernel 提供的是「确定性机制」——状态机、幂等、栅栏、预算、恢复——这些机制能保证一个 Agent 在中断、重试、并发下**不重不漏**，但它们是一个个零件。runtime 把零件装成整车：你给一个模型接口、一组工具，就能 `Run` 起一个会话。

## 小白类比：外卖平台与骑手

| 类比 | 对应 |
|---|---|
| 你开的餐馆（只做菜） | **宿主产品**：只写提示词、工具、模型适配 |
| 外卖平台的调度系统 | **runtime**：接单、派单、跟踪、兜底 |
| 平台规则（一单不送两次、超时怎么判） | **kernel**：判据——幂等闸、预算守卫、恢复语义 |
| 道路与电动车 | **oagentkit / oekit**：上游原语 |

餐馆老板不需要懂调度算法，只需要把菜做好；同样，宿主不需要懂幂等键怎么铸造，只需要把工具注册对。

## 为什么它是独立仓库

1. **门禁隔离**：kernel 的门禁核心是「内核包不拖存储驱动」。装配层必须直接装配 SQLite/PG 驱动与事件面，放进来会把那条判据开口子。
2. **发版节奏不同**：Runtime 的 Beta/RC/1.0 是产品层节奏，与 kernel 的机制版各发各的。

## 三套形态，各自解决什么

| 形态 | 落点 | 解决的问题 |
|---|---|---|
| embedded | 内存 | 单进程、测试、内嵌——零外部依赖，进程退出即丢 |
| standalone | SQLite 单文件（WAL） | 本机服务——进程重启后接着跑，历史不丢 |
| cluster | PostgreSQL + worker 池 | 多副本共享 PG——同一会话集群内只有一个副本执行，副本崩了别的副本接管重跑 |

cluster 的前置是 kernel 两项 P0 已修复并发布（控制面权威介入原子审计 v0.64.3、租约持续故障失格 v0.64.1）；判据仍全部来自 kernel，本仓只做接线。

**前提要说在前面**：接管后要「不重复施加副作用」，靠宿主声明**业务幂等键**（订单号这类稳定键）；未声明时沿用编排侧铸造的 `toolCallID`，跨副本接管这一步依赖模型给出稳定的 `tool_call_id`。

**证据**：cluster 的集成用例跑真 PostgreSQL——投递 → 执行 → 结果经事件面回传；两个独立副本抢同一会话时工具只被施加一次；副本领了任务却不收场（模拟被 SIGKILL）后另一副本接管，已施加的副作用不再施加。CI 的 integration job 提供真 PostgreSQL 跑这批用例；没有库时显式 skip，不伪造结果。
