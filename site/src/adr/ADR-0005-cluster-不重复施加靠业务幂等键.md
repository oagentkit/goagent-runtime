| 项 | 内容 |
|---|---|
| **状态** | 已采纳（Accepted） |
| **日期** | 2026-11-23（cluster 模板落地，v0.4.0） |
| **背景** | cluster 模板让多个副本共享一个 PostgreSQL：同一会话在集群内**有且只有一个副本执行**，副本崩了由别的副本接管重跑。要让「接管重跑」不重复施加工具副作用，就需要一个跨副本稳定的幂等键。默认的 `toolCallID` 是**编排侧铸造**的，跨副本这一步要靠模型给出稳定的 `tool_call_id`——不可靠。 |
| **决策** | 宿主可声明**业务幂等键** `pipeline.Tool.IdempotencyKey`（如订单号这类业务语义决定的稳定键）。声明后，同一业务动作无论由哪个副本施加都算同一次，闸判 `replayed`；未声明时沿用编排侧铸造的 `toolCallID`，此时跨副本这一步依赖模型给出稳定 ID。**能力、前提、证据三段式写进文档**，不吹「绝对不重复」。 |
| **后果** | ① 想要「接管后绝不重复施加」的宿主必须声明业务幂等键——这是**显式的前提**，不是隐式保证；② 不声明也能用，但跨副本这一步的强度依赖模型，属已写明的局限；③ 前置条件落在 kernel 侧两项 P0（控制面权威介入原子审计 v0.64.3、租约持续故障失格 v0.64.1），判据仍全部来自 kernel 的 `taskboard` / `sideeffect`。 |
| **依据** | 仓内 README「cluster：多副本形态（PG + worker 池）」；`site/src/templates/README.md` 的「能力 / 前提 / 证据」三段；kernel 的 `taskboard` 与 `sideeffect` 契约包。 |

&gt; **一句话结论**：「接管不重复施加副作用」的前提是宿主声明业务幂等键——这是结构性保证，不靠模型复述同一个 ID。

---

## 两种强度的「不重复施加」

| | 幂等键来源 | 强度 |
|---|---|---|
| 同进程恢复重放 | 编排侧铸造的 `toolCallID` | **结构性**：同一回合内它一定稳定 |
| 跨副本接管重跑 | 宿主声明的 `pipeline.Tool.IdempotencyKey` | **结构性**：由业务语义决定，跨副本也稳定 |
| 跨副本接管重跑（未声明） | 编排侧铸造的 `toolCallID` | **依赖模型**：要求模型给出稳定的 `tool_call_id` |

第三行是本 ADR 存在的理由：它**能用**，但强度是「模型通常会给稳定 ID」，
而不是「系统保证不会重复」。把这两者混着说，就是吹没兑现的自白。

## 为什么键由业务决定

`toolCallID` 表达的是「这一次调用」，`IdempotencyKey` 表达的是「这一笔业务」。
订单号天然跨副本、跨重试、跨时间稳定；调用 ID 不是——它由编排侧在运行时铸造，
接管重跑时那份上下文已经不是同一个了。

## 证据形态

集成用例跑**真 PostgreSQL**（`cluster/pg_cluster_test.go`）：

- 两个独立副本抢同一会话时，工具只被施加一次；
- 副本领了任务却不收场（模拟被 SIGKILL）后另一副本接管，已施加的副作用不再施加。

CI 的 integration job 提供真 PostgreSQL 跑这批用例；没有库时用例显式 skip，**不伪造结果**。
