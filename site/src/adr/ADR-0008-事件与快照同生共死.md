---


| 项 | 内容 |
|---|---|
| **状态** | 已采纳（Accepted） |
| **日期** | 2026-11-23（#2 主体落地 SQLite 形态；#9 收口 PG 形态与判据口径） |
| **背景** | 事件面与快照面原先是**两次提交**：先落快照，再落事件行。两次之间进程死掉 ⇒ 两种残缺形态：① 快照已落、事件未落 ⇒ 终态事件丢失（宿主等不到收场）；② 事件已落、快照未落 ⇒ 孤儿事件（恢复后重放，把已经发生过的事再做一遍）。这两个窗口都不是「模型算错」，而是**提交顺序**的结构性缺口。 |
| **决策** | 事件行与快照行**同生共死**：两脸同库时走**单事务**联合提交（`CommitWithEvents`）——快照 CAS 与事件 insert 在同一事务里，任一面失败整批回滚。loop 侧：Joint 形态下 `emit` 只累计不发送，`commit` 时随快照一起提交，提交成功后统一广播。 |
| **后果** | ① 孤儿事件/终态丢失两个窗口结构闭合（不是「概率降低」，是**不存在**）；② 联合提交失败时**本批事件作废**（重试的形态是重跑该回合，新一轮重新产生事件；把上一批挂着等下一轮提交等于把两轮事件混进同一笔快照）；③ 「一轮四事件」（2×`round_start` + `tool_call` + `session_state`）成为**可机判的口径**；④ 流式增量是观测面不是状态面 ⇒ **不进**联合事务（见 ADR-0009）；⑤ PG 形态靠 cluster 的**显式接线**（`Joint: c.store`，编译期保证），而不是 runtime 的类型断言——`pgstore.Store` 不是 `storage.Provider`，走的是 cluster 模板。 |
| **依据** | runtime issue #2（主体）、#9（PG 形态与判据口径）；仓内 `agentloop/joint.go`、`pgstore/joint.go`、`sqliteadapter` 的 `CommitWithEvents`；`storage/sqlitestore/joint_test.go` 与 `pgstore/joint_test.go` 两处原子性直证。 |

&gt; **一句话结论**：事件与快照同生共死——两脸同库时单事务联合提交，孤儿事件与终态丢失两个窗口结构闭合。

---

## 两种形态

| 形态 | 事件面 | 事务耦合 |
|---|---|---|
| Joint（两脸同库：SQLite / PG） | 事件行随快照单事务落库 | 有（同生共死） |
| 两步（事件面与快照面不同库） | 事件由 emitter 即时发 | 无（残留窗口） |

runtime 装配**自动检测**：存储实现 `storage.JointCommitter` 且有事件面 ⇒ 走 Joint；否则回落到两步旧路径（向后兼容）。

## 判据（原子性直证）

「同生共死」不能只写在文档里——它有两条可证伪的断言：

1. **事件行零落**：联合提交失败（快照 CAS 拒收陈旧快照）⇒ 整批回滚 ⇒ 事件行一个都不落（不是落一半）；
2. **快照行不落**：事件面失败 ⇒ 快照行同样不推进（「同生共死」的另一半；两侧形态均已补上——注入一个不可序列化的 payload 让事件面必失败）。

用例落在 `storage/sqlitestore/joint_test.go`（SQLite 形态）与 `pgstore/joint_test.go`（PG 形态，真 PG 跑，见 CI 的 integration 作业）。
